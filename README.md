# Проект: Веб-сервис бронирования помещений (RoomBooking)

## 1. Цель работы
Освоение базовых этапов проектирования программного обеспечения путем разработки концепции веб-приложения для бронирования помещений и подготовки технического задания (ТЗ).

---

## 2. Описание предметной области
Современные компании, коворкинги, образовательные учреждения и отели часто сталкиваются с проблемой неэффективного использования переговорных комнат, лекционных залов или других помещений общего пользования. Бумажные графики или устные договоренности приводят к путанице, «двойному бронированию» или простоям.

**Акторы системы:**
*   **Пользователь (Сотрудник/Клиент):** Желает быстро найти свободное помещение под свои задачи (совещание, тренинг, встреча) и забронировать его на определенное время.
*   **Администратор:** Отвечает за настройку системы: добавляет/удаляет помещения, управляет пользователями, отслеживает общую загрузку и разрешает конфликтные ситуации.

**Сущности:**
*   **Помещение:** Обладает названием, вместимостью, списком оборудования (проектор, флипчарт), фотографиями и местоположением (этаж/корпус).
*   **Бронь:** Запись о событии, содержащая временной слот (дата, начало, конец), ID пользователя, ID помещения и описание встречи.
*   **Пользователь:** Данные для входа, имя, контактная информация, роль (админ или обычный пользователь).

## 3. Формализация требований (ТЗ)

### Функциональные требования
1.  **Управление помещениями (CRUD):** Администратор должен иметь возможность добавлять новые помещения, редактировать их характеристики (название, вместимость, фото) и удалять устаревшие.
2.  **Просмотр расписания:** Пользователь видит сетку доступности помещений на день/неделю с фильтрацией по дате, вместимости и оснащению.
3.  **Создание брони:** Пользователь выбирает свободный слот и создает бронь, указывая название мероприятия.
4.  **Управление бронями:**
    *   Пользователь видит список своих будущих броней и может их отменить.
    *   Администратор видит все брони и может отменить любую (в случае форс-мажора).
5.  **Аутентификация:** Вход в систему по email и паролю, разделение прав (пользователь/администратор).

### Нефункциональные требования
1.  **Безопасность:** Доступ к управлению помещениями только для администраторов. Пароли хранятся в хешированном виде.
2.  **Надежность:** Система должна исключать возможность двойного бронирования на один и тот же временной слот для одного помещения (race conditions должны быть обработаны на уровне БД и сервера).
3.  **Удобство (UX):** Интуитивно понятный интерфейс, не требующий обучения.
4.  **Производительность:** Время загрузки страницы с расписанием не должно превышать 2 секунд при средней нагрузке.

## 4. Выбор технологического стека (Проектирование архитектуры)

### 4.1. Бэкенд (Server-Side)
*   **Язык:** Python 3.11+
*   **Фреймворк:** FastAPI
    *   *Обоснование:* Высокая производительность, асинхронность, автоматическая генерация документации OpenAPI (Swagger), что упрощает тестирование API.
*   **База данных:** PostgreSQL
    *   *Обоснование:* Надежная реляционная СУБД, необходимая для поддержания целостности данных (ограничения уникальности для временных слотов), поддержка JSON полей при необходимости.
*   **ORM:** SQLAlchemy 2.0 + Alembic (для миграций)
*   **Аутентификация:** JWT (JSON Web Tokens) с использованием `python-jose` и `passlib` (bcrypt).

### 4.2. Фронтенд (Client-Side)
*   **Фреймворк:** React.js (с использованием хуков)
*   **Управление состоянием:** React Context API / Redux Toolkit (если форма станет сложной).
*   **UI библиотека:** Ant Design или Material-UI (для ускорения разработки интерфейса администрирования и календаря).
*   **HTTP-клиент:** Axios.

### 4.3. Инфраструктура
*   **Контейнеризация:** Docker + Docker Compose (для запуска БД, бэкенда и фронтенда одной командой).
*   **Веб-сервер:** Nginx (как reverse proxy).

## 5. Проектирование интерфейса пользователя (UI/UX)

### 5.1. Структура страниц (Site Map)
1.  **Страница входа (Login):** Поля Email/Пароль.
2.  **Главная (Dashboard):** Календарь/расписание. Фильтры сверху.
3.  **Карточка помещения:** Детальная информация и кнопка "Забронировать" (или выбор слота прямо в календаре).
4.  **Личный кабинет:** Список моих броней с возможностью отмены.
5.  **Админ-панель:** Отдельный раздел для редактирования списка помещений.

### 5.2. Примерный макет (Dashboard)
*   Левая панель: Список помещений с чекбоксами (фильтр).
*   Основная область: Сетка "Время по вертикали / Помещения по горизонтали".
    *   Занятые слоты выделены цветом (например, синим).
    *   При клике на свободный слот открывается модальное окно "Новая бронь" с полем "Название мероприятия".

## 6. Предварительное проектирование API и структуры данных

### 6.1. Модели данных (БД)

**Таблица `users`**
| Колонка     | Тип         | Описание                         |
|-------------|-------------|----------------------------------|
| id          | UUID (PK)   | Первичный ключ                   |
| email       | String(100) | Уникальный email                 |
| hashed_pass | String      | Хеш пароля                       |
| full_name   | String      | Полное имя                       |
| role        | Enum        | 'user' или 'admin'               |
| created_at  | Timestamp   | Дата регистрации                 |

**Таблица `rooms`**
| Колонка       | Тип         | Описание                         |
|---------------|-------------|----------------------------------|
| id            | UUID (PK)   | Первичный ключ                   |
| name          | String(100) | Название (напр. "Переговорная А")|
| capacity      | Integer     | Вместимость                      |
| location      | String      | "Этаж 3, крыло Б"                |
| description   | Text        | Описание и оснащение             |
| image_url     | String      | Ссылка на фото                    |

**Таблица `bookings`**
| Колонка       | Тип         | Описание                                   |
|---------------|-------------|--------------------------------------------|
| id            | UUID (PK)   | Первичный ключ                             |
| room_id       | UUID (FK)   | Внешний ключ на `rooms.id`                 |
| user_id       | UUID (FK)   | Внешний ключ на `users.id` (кто забронировал)|
| title         | String      | Название встречи                            |
| start_time    | Timestamp   | Начало брони (включая дату)                |
| end_time      | Timestamp   | Конец брони                                 |
| created_at    | Timestamp   |                                             |

> *Ограничение:* Уникальный индекс на пару (`room_id`, `start_time`) для защиты от двойных броней.

### 6.2. Эндпоинты API (REST)

**Аутентификация**
*   `POST /auth/register` - Регистрация.
*   `POST /auth/login` - Вход, получение JWT токена.

**Пользователи**
*   `GET /users/me` - Получить профиль текущего пользователя.

**Помещения (Rooms)**
*   `GET /rooms` - Получить список всех помещений (с фильтрацией по capacity).
*   `GET /rooms/{id}` - Получить детали конкретного помещения.
*   `POST /rooms` (Admin) - Создать новое помещение.
*   `PUT /rooms/{id}` (Admin) - Обновить данные помещения.
*   `DELETE /rooms/{id}` (Admin) - Удалить помещение.

**Брони (Bookings)**
*   `GET /bookings/my` - Получить брони текущего пользователя.
*   `GET /bookings?room_id=&date=` - Получить брони для конкретной комнаты на дату.
*   `POST /bookings` - Создать новую бронь.
*   `DELETE /bookings/{id}` - Отменить бронь (с проверкой прав: либо владелец, либо админ).
